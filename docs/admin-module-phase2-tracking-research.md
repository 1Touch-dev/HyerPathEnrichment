# Admin Module — Phase 2 Moderation & Review Queue: Tracking Research

**Date:** 2026-08-20
**Status:** Research only — captures the sources behind decisions already made in this batch's plan; cross-checked against this codebase's actual current state, matching the rigor of `docs/admin-module-research.md`.
**Scope:** The Phase 2 moderation/review-queue layer of the Admin Module — a generic `admin_review_queue` table plus per-domain moderation columns on `job_postings`, `candidate_documents`, `portfolio_profiles`, and `outreach_messages` (see `phase2_admin_module.md` and `docs/adr/0016-phase2-moderation-review-queue.md`). This document is a research trail, not an implementation spec — it exists so a future reader can see *why* each design choice was made, not just *what* was built.

**Labeling convention used throughout (same as `docs/admin-module-research.md`):**
- ✅ **DIRECT** — the cited source explicitly documents this practice, or the claim was verified directly against this repo's own code.
- 🟡 **INDIRECT** — the cited source documents a closely analogous pattern in a different domain or product, applied here by inference.
- ❌ **NOT FOUND** — no external corroboration found in this research session; flagged as opinion/repo-derived reasoning only, not a verified external claim.

## 1. Indeed's Trust & Safety approach

| Claim | Source | Label |
|---|---|---|
| Job postings, company pages, and messages are subject to automated risk-signal flagging combined with human moderator review queues, plus a per-item user reporting mechanism that feeds the same queue | Indeed Digital Services Act Transparency Report — [indeed.com/legal/digital-services-act-transparency-report](https://www.indeed.com/legal/digital-services-act-transparency-report) | ✅ **DIRECT** |

**Practical take:** this is the closest same-product-category precedent available — Indeed is a job board/job-search platform moderating exactly the resource types this plan targets (job postings, and by extension user-generated profile/message content). The DSA transparency report format is itself evidence of the underlying architecture: it discloses volumes of automated detections vs. user reports vs. resulting human decisions, which only makes sense if automated flagging and human review are two distinct stages feeding one decision queue — the same two-stage shape (`flag_source: heuristic|llm_judge` feeding a human `decide` action) this plan's `admin_review_queue` table implements. Since Indeed is the single most directly comparable public precedent (same product category, not an analogy from payments or SaaS), it's cited first and weighted highest of the sources in this document.

## 2. Stripe Radar's review-queue model (cross-reference)

| Claim | Source | Label |
|---|---|---|
| A rule or model flags an item, the item lands in a review queue, the queue exposes a list view (scan without opening) and a detail view (full context to decide), and an explicit approve/reject action closes the item and is recorded as a `review.opened`/`review.closed` event | Stripe Radar review-queue docs — [docs.stripe.com/radar/reviews](https://docs.stripe.com/radar/reviews) | ✅ **DIRECT**, reused as this plan's queue shape |

**Practical take:** this is not new research — it's the same source already cited in §4 of `docs/admin-module-research.md` for the CV-review-queue pattern, cross-referenced here because this plan's generic `admin_review_queue` table is the literal generalization of that earlier, narrower recommendation. Where the original research doc scoped this pattern to CVs only (`status` field on the CV/parse record), this plan lifts the same list→detail→decide→event shape out into a domain-agnostic table (`resource_type`/`resource_id` polymorphic key, `status`, `flag_reason`, `flag_source`, `reviewed_by`/`reviewed_at`/`review_notes`) so it applies uniformly to job postings, documents, portfolio items, and outreach messages rather than being rebuilt per domain. `backend/app/modules/admin/review_queue_router.py`'s `list_review_queue` (scan), `get_review_queue_item` (detail, via `_resolve_resource`'s raw-SQL snapshot of the underlying row), and `decide_review_queue_item` (approve/reject, recorded via `record_admin_action`) map directly onto Stripe's list view / detail view / explicit action / recorded event structure. Labeled ✅ DIRECT here (rather than 🟡 INDIRECT as in the original doc's §4) because this plan's queue is now a payments-adjacent fraud/abuse queue shape applied to a strictly analogous problem — a generic content-moderation queue — not a CV-specific reinterpretation; the structural fit is closer than the original CV framing was.

## 3. Cascade moderation architecture

| Claim | Source | Label |
|---|---|---|
| Production content-moderation systems route the bulk of traffic through cheap tiers (keyword/deny-list, then a lightweight classifier) and escalate only ambiguous cases to an LLM-as-judge, reserving human review for the hardest/most consequential remainder — a waterfall, not a single decision gate | "LLM Content Moderation at Scale" — [tianpan.co/blog/2026-04-12-llm-content-moderation-at-scale](https://tianpan.co/blog/2026-04-12-llm-content-moderation-at-scale); corroborated by "AI Content Moderation 2026: An LLM Trust-Safety Guide" — [digitalapplied.com/blog/ai-content-moderation-2026-llm-trust-safety-guide](https://www.digitalapplied.com/blog/ai-content-moderation-2026-llm-trust-safety-guide) and "Design a Content Moderation System at Scale" — [hld.handbook.academy/curriculum/case-studies/content-moderation-at-scale](https://hld.handbook.academy/curriculum/case-studies/content-moderation-at-scale/) | 🟡 **INDIRECT** as applied to this stack |
| A moderation reviewer/classifier stage should be wrapped so that on failure (timeout, error, degraded confidence) it degrades to pass-through rather than blocking the underlying action — "fail-open with a circuit breaker," with the fallback value being the primary decision passed through unmodified, not a queue-and-retry or a hard block | "Fail-Open LLM Architecture: Why Your Reviewer Stage Should Never Block a Decision" — [dev.to/a3e_ecosystem/fail-open-llm-architecture-why-your-reviewer-stage-should-never-block-a-decision-1bd9](https://dev.to/a3e_ecosystem/fail-open-llm-architecture-why-your-reviewer-stage-should-never-block-a-decision-1bd9); corroborated by "The Guardrail's Failure Mode Is Always 'Allow'" — [dev.to/aiexplore369zoho/the-guardrails-failure-mode-is-always-allow-2a6p](https://dev.to/aiexplore369zoho/the-guardrails-failure-mode-is-always-allow-2a6p) | 🟡 **INDIRECT** as applied to this stack |
| Fail-open vs. fail-closed is not a universal policy — it should be tiered by consequence: catastrophic/irreversible-harm categories (e.g. CSAM) fail closed, everything else defaults to fail-open with heavier downstream logging and async re-check, because a universal fail-closed policy turns one flaky dependency into a platform outage | "How We Made Moderation Architecturally Impossible to Skip" — [dev.to/candornetwork/how-we-made-moderation-architecturally-impossible-to-skip-7lo](https://dev.to/candornetwork/how-we-made-moderation-architecturally-impossible-to-skip-7lo); "Chapter 118: Design a content moderation pipeline" — [kunwar.page/chapter/118-design-a-content-moderation-pipeline](https://www.kunwar.page/chapter/118-design-a-content-moderation-pipeline) | 🟡 **INDIRECT** — these sources describe UGC platforms at a scale and harm-severity range (CSAM, terrorism content) well beyond this plan's scope, but the underlying tiering logic ("some categories can never fail open, most can") is exactly why this plan's `flag_if_needed()` is unconditionally fail-open: nothing this plan flags (spam-like text, policy-violating language in job postings/documents/portfolio items/outreach messages) is in the catastrophic/irreversible tier those sources reserve for fail-closed handling |

**Practical take:** all four sources above are generic UGC/trust-and-safety engineering write-ups (SaaS moderation vendors, HLD interview-prep material, independent engineering blogs), not job-platform-specific — hence 🟡 INDIRECT rather than ✅ DIRECT, consistent with this document's labeling convention. But the shape transfers cleanly for two reasons specific to what this plan actually builds. First, this plan only builds automated *flagging into a human queue*, never automated *removal/enforcement* — `backend/app/modules/admin/moderation_flagging.py`'s `flag_if_needed()` creates an `AdminReviewQueueItem` and nothing else; the only code path that changes a domain resource's visibility (`_flip_domain_column()` in `review_queue_router.py`) runs strictly after a human's `decide` action, never automatically. That is a strictly lower-risk version of what these sources describe (they're reasoning about automated *enforcement* pipelines with real fail-open/fail-closed stakes at the point of publish/block; this plan's automation only ever populates a queue for a human to look at). Second, `run_llm_judge()`'s own `try`/`except Exception: return False, None` and `flag_if_needed()`'s outer `try`/`except Exception: ... return None` are exactly the "reviewer stage returns the pass-through/no-flag default on any failure" pattern the fail-open source describes, applied to the one place in this plan where an LLM call could otherwise raise and block a worker task's own create/update action. No dedicated circuit breaker (half-open probe, failure-rate counter) exists in this plan's code — the research honestly surfaces that as a gap, not something to paper over; see the ADR's Consequences section for this being flagged as intentionally deferred, not missed.

## 4. Audit-log best practice (Stripe Activity Logs pattern)

| Claim | Source | Label |
|---|---|---|
| An audit/activity log entry should record actor, action type, timestamp, and affected resource, and role/state-change entries specifically should record both the old and new values rather than just "changed" | Stripe Activity Logs API — [docs.stripe.com/activity-logs](https://docs.stripe.com/activity-logs); object schema — [docs.stripe.com/api/v2/iam/activity-logs/object](https://docs.stripe.com/api/v2/iam/activity-logs/object) | ✅ **DIRECT** |

**Practical take:** this is the same source already cited in §7 and §11.2 of `docs/admin-module-research.md`, cross-referenced here because this plan's review-queue decision writes are just another `record_admin_action()` call site, not a new logging mechanism. `backend/app/modules/admin/audit.py:50-61`'s `record_admin_action()` already accepts and persists `before: dict[str, Any] | None` and `after: dict[str, Any] | None` as JSON columns on `AdminAuditLog`, and `review_queue_router.py`'s `decide_review_queue_item()` calls it with `before={"status": item.status}` (the pre-decision state) and `after={"status": payload.status, "review_notes": payload.review_notes}` (the post-decision state) — the exact actor/action/timestamp/before-after shape Stripe's Activity Log object documents, verified directly against this plan's own code, not asserted from the vendor doc alone. No schema change was needed for this plan: `AdminAuditLog` already existed (Admin Module Batch 0/1, `docs/adr/0015-admin-module-rbac-audit-mfa.md` Decision 3) with generic `before`/`after` JSON columns wide enough to hold any domain's moderation-decision payload.

## 5. Hash-chained / append-only ledger audit stores

| Claim | Source | Label |
|---|---|---|
| Hash-chained (or HMAC-chained) audit logs — where each row's hash is computed over its own fields plus the previous row's hash, making tampering detectable via a chain-walk verifier — are a real, documented pattern, but the sources describing it are explicitly framed around SOC 2 evidence requirements (CC6.1, CC7.2), multi-tenant SaaS with per-tenant chains, HIPAA/BAA-grade health data, or "an insider with full database access" threat models | "How to build an immutable audit log with HMAC hash chaining" — [tracehold.ai/blog/immutable-audit-log-hmac-hash-chain](https://tracehold.ai/blog/immutable-audit-log-hmac-hash-chain/); "Hash Chaining for Tamper-Proof Audit Logs Explained" — [auditkit.dev/blog/hash-chaining-tamper-proof-audit-logs](https://auditkit.dev/blog/hash-chaining-tamper-proof-audit-logs); "Immutable by Design: Building Tamper-Proof Audit Logs for Health SaaS" — [dev.to/beck_moulton/immutable-by-design-building-tamper-proof-audit-logs-for-health-saas-22dc](https://dev.to/beck_moulton/immutable-by-design-building-tamper-proof-audit-logs-for-health-saas-22dc) | ❌ **NOT FOUND** to be warranted here (see reasoning below) |

**Practical take:** the sources above are real and were actually found (not fabricated), but every one of them frames hash-chaining as solving a specific problem this repo does not currently have: proving to an external SOC 2/HIPAA auditor, or to a multi-tenant customer, that not even a privileged insider with direct database access altered historical rows, typically layered with database-level append-only triggers and external anchoring (S3 Object Lock, KMS) on top of the hash chain itself. This repo's `AdminAuditLog` (`backend/app/modules/admin/models.py`, per `docs/adr/0015`) is a single-tenant, internal admin-trail table — there is no external auditor requiring chain-of-custody proof today, no multi-tenant boundary to scope a per-tenant chain to, and no compliance framework (SOC 2, HIPAA) this repo has committed to that mandates it (this repo's actual compliance surface is LGPD/GDPR candidate-data handling via the separate `compliance.AuditLog`/opt-out system, per `docs/adr/0004` and `docs/adr/0005` — a different table with a different, already-settled purpose per `docs/adr/0015` Decision 3). Adding hash-chaining now would mean solving a threat model (a compromised or malicious admin/DBA tampering with `admin_audit_logs` after the fact) that has not been identified as a real risk at this repo's current scale and team size, at the cost of a deterministic canonicalization scheme, an advisory-lock-guarded read-hash-write cycle, and a verifier job that must run somewhere — real ongoing complexity for a threat that isn't on this project's radar. The existing single `AdminAuditLog` table, with router-level explicit calls plus `AdminAuditFallbackMiddleware`'s best-effort safety net (per `docs/adr/0015` Decision 4), is proportionate to "an internal admin trail a support/eng team can trust for attribution," which is this repo's actual current bar — not "cryptographically provable to a third-party auditor." If a SOC 2 engagement or a hostile-insider threat model becomes real, hash-chaining should be revisited then, per this doc's convention of ❌ NOT FOUND flagging opinion/reasoning rather than fabricating a citation for it.

## 6. Appeals path

| Claim | Source | Label |
|---|---|---|
| A real trust & safety system needs a mandatory error-correction channel: users must be able to challenge an enforcement decision, appeals should be reviewed by someone other than the original decision-maker, and the platform must communicate the specific rule applied and the outcome, not a generic message | "The best practices for moderation appeals" — [partnerhero.com/blog/best-practices-for-moderation-appeals](https://www.partnerhero.com/blog/best-practices-for-moderation-appeals); "How to Handle Appeals and Disputes in Content Moderation" — [omaccanada.ca/2026/02/17/how-to-handle-appeals-and-disputes-in-content-moderation-a-practical-workflow](https://omaccanada.ca/2026/02/17/how-to-handle-appeals-and-disputes-in-content-moderation-a-practical-workflow/) | 🟡 **INDIRECT** here |

**Practical take:** both sources are real, general trust-and-safety operations guidance (not job-platform-specific, hence 🟡 INDIRECT rather than ✅ DIRECT), and both are unambiguous that an appeals channel is not optional for any system that takes enforcement action against user content or accounts — one even frames "who can appeal" as covering *any* decision taken on a user's content or account. A full candidate-facing self-serve appeal UI (structured intake form, independent-reviewer routing, SLA tracking, outcome templates) is explicitly out of scope for this plan — building that is a multi-day feature in its own right, not a natural extension of a review-queue table. Instead, this plan reuses the existing notification/email worker: `decide_review_queue_item()`'s rejection path calls `_lookup_notify_email()` to resolve the affected user's email (skipping `job_posting`, which has no owning candidate, and the Module 3 placeholders) and, on success, `enqueue_email("moderation_decision", email, {"resource_type": ..., "reason": ...})`. That notification is the manual error-correction channel this plan actually ships: an affected user learns their document was removed or their outreach message was blocked and why, and can reply to that email or open a support ticket to contest it — satisfying the "users must be able to challenge a decision" requirement via an existing support workflow rather than a new UI surface. A self-serve in-app appeal flow (structured intake, independent-reviewer assignment, an `appeal_status` alongside `moderation_status`) is flagged here as explicit future work, not a gap this plan silently leaves unaddressed.

## Ground truth already mapped

Before this batch, none of the four domains this plan touches had any moderation surface at all:

- **No moderation columns existed** on `JobPosting`, `CandidateDocument`, `PortfolioProfile`, or `OutreachMessage` prior to this plan — `moderation_status`/`moderated_by`/`moderated_at` (job postings), `deleted_at` (documents), `admin_hidden` (portfolio profiles), and `admin_blocked` (outreach messages) are all net-new columns added by `alembic/versions/040_phase2_moderation_columns.py`.
- **Zero existing admin escape hatches existed** in those four domains — there was no way for an admin to hide a job posting, soft-delete a document, hide a portfolio profile, or block an outreach message before this plan's `job_postings_router.py`, `portfolio_router.py`, `outreach_router.py`, and the generic `review_queue_router.py` were added.
- **`documents.delete_document()` was a hard delete** before this plan — `backend/app/modules/documents/service.py:434-460`'s existing candidate-facing delete endpoint calls `await self.db.delete(document)` directly (relying on cascade deletes for embeddings/jobs), with no soft-delete column to set instead. This plan's `deleted_at` column is additive to the schema but does not yet change that candidate-facing delete path's behavior — it is populated today only via the review-queue's rejection flip (`_flip_domain_column()`'s `document` branch), not by the candidate's own delete action.
- **Portfolio's public route was fully unauthenticated**, so hiding a moderated profile required intercepting that exact handler rather than relying on any auth-layer gate: `backend/app/modules/portfolio/service.py:107-111`'s `get_public_profile()` is reached by an unauthenticated `/p/{slug}` page, and its existing 404-on-not-found/not-published branch was the only place `admin_hidden` could be enforced (`if not profile or not profile.is_published or profile.admin_hidden: raise HTTPException(...)`).

Reusable pieces this plan builds on rather than reinvents:

- `require_permission(resource, action)` (RBAC dependency from the earlier Admin Module batch, `docs/adr/0015`) gates every new endpoint in this plan (e.g. `require_permission("content_review", "read"/"decide")`, `require_permission("job_postings", "moderate")`, `require_permission("portfolio", "moderate")`).
- `record_admin_action()` (`backend/app/modules/admin/audit.py:50-61`) is called explicitly at every decision point in this plan (review-queue decide, job-posting moderate, portfolio moderate), with `AdminAuditFallbackMiddleware`'s `/api/admin`-prefix check as the defense-in-depth backstop for any mutating admin route in this plan that forgets an explicit call.
- The async-job-chain-to-queue idiom already used elsewhere in this repo (workers enqueueing follow-up work rather than doing it inline) is mirrored by this plan's flagging cascade running inside the existing worker task path rather than as a separate service.
- The LLM-as-judge JSON-mode call pattern in `moderation_flagging.py`'s `run_llm_judge()` is deliberately the same `httpx.AsyncClient` + OpenAI `response_format: {"type": "json_object"}` shape as `backend/app/services/cv_extractor.py`, reused rather than reinvented for this plan's classifier step.
- The `frontend/features/admin/` layout convention (a `components/`, `hooks/`, and `api/` subfolder per admin capability, e.g. `AnalyticsPanel.tsx` + `useAnalytics.ts` + `api/client.ts`) is the structure this plan's moderation UI is expected to follow when it lands, matching every other Admin Module panel already in that folder.
